# Security

How the platform protects accounts and data, what is tested, and what is deliberately out of
scope. To report a vulnerability, open a private security advisory on the GitHub repository
rather than a public issue.

## Threat model

Three things are treated as untrusted:

1. **Requests** — anything a browser or script sends.
2. **Uploaded files** — names, types, structure and every cell value.
3. **Model output** — tool names, tool arguments and report text produced by the LLM.

The assets to protect are user accounts, each user's datasets and reports, the server itself,
and the correctness of the numbers in a report.

## Controls

### Authentication and sessions

- Passwords are hashed with **Argon2id** (argon2-cffi defaults) and rehashed on login when
  parameters change. Minimum length is 10 characters; all-digit and near-constant passwords
  are rejected.
- Login verifies a hash even when the account does not exist, and returns the same message
  for an unknown email and a wrong password.
- Sessions are opaque 256-bit tokens. Only a SHA-256 digest is stored, so a database leak does
  not yield usable sessions. Logout deletes the session server-side. Changing the password
  revokes every other session.
- The session cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` in production.

### CSRF

Every state-changing request authenticated by cookie must carry an `X-CSRF-Token` header equal
to the readable `awa_csrf` cookie (double-submit). A page on another origin can neither read
the cookie nor set the header. CORS never allows credentials.

### Authorisation and tenant isolation

Every query for a user-owned resource filters on the authenticated user's id in the service
layer. A resource that belongs to someone else returns **404 with the same body as a
nonexistent id**, so ids cannot be probed. Storage keys are namespaced by user id and are
generated by the server.

`tests/test_isolation.py` exercises all 17 resource routes as the wrong user and as an
anonymous caller, checks that failed attempts change nothing, and checks that an analysis run
never sees another user's data.

### Upload handling

- File type is established from the bytes, not the name or the `Content-Type` header.
- The client's filename is reduced to a display label and is never used in a path.
- `.xlsx` archives are checked for entry count, total uncompressed size and compression ratio
  before they are opened (zip bombs). `defusedxml` is installed, which openpyxl uses to refuse
  XML entity-expansion attacks.
- Spreadsheet **formulas and macros are never executed**; only stored cell values are read.
  `.xlsm` is not accepted.
- Request size is checked from `Content-Length` before the body is read, and again while
  streaming. Rows, columns and cells are capped during parsing.
- Per-user quotas apply to dataset count and stored bytes.

### No model-controlled code execution

The original CLI passed a model-written string to `DataFrame.query()`, which evaluates Python
expressions. That path is gone:

- **Filters** are data: a column, an operator from a fixed list, and a value compared with
  ordinary pandas operations. Text matching is literal, never a regular expression.
- **Calculated columns** accept arithmetic only. The expression is parsed with `ast` and
  evaluated by walking the tree: numbers, column names and `+ - * /` are accepted, everything
  else is rejected before any evaluation. `eval`, `exec` and `DataFrame.query` are not used
  anywhere in the codebase.
- **Tool calls** are validated against Pydantic schemas with unknown fields forbidden. No tool
  accepts a path, URL, dataset id or code.

`tests/test_expressions_security.py` runs about thirty injection payloads through these paths.

### Prompt injection

A cell can contain text that reads like an instruction. Defences, in order of strength:

1. **Structural.** The agent has no tools that write, send or fetch anything, and its tools
   are bound to one dataset. A successful injection cannot reach other users' data, the
   network or the filesystem. The worst outcome is a misleading report about the attacker's
   own file.
2. **Numeric grounding.** Results are computed by pandas regardless of what a cell says. If
   the model were persuaded to state a different figure, the grounding check flags it.
3. **Fencing.** Before any cell text reaches a prompt it is flattened to one line, truncated,
   and stripped of angle brackets and backticks, then wrapped in a delimited block that the
   system prompt declares to be data and never instructions.

The third layer reduces the chance that a model follows injected text; it cannot make it
impossible. The first two do not depend on the model behaving.

### Limits of verification

The grounding check proves that each **number** in a report's factual sections matches a
computed value. It does not prove that the surrounding sentence describes that number
correctly — a model can still attach a correct figure to the wrong label, or draw a conclusion
the data does not support. Mitigations: tools label their own output unambiguously (for
example, period comparisons always report earlier-to-later regardless of argument order), the
report prompt forbids relabelling, and every claim links to its evidence so a reader can
check it. Recommendations and limitations are advice and are not checked.

### Export safety

Dataset values are attacker-controlled, so text cells beginning with `=`, `+`, `-`, `@`, tab
or carriage return are prefixed with an apostrophe in Excel and CSV exports. This stops
spreadsheet applications from executing them as formulas.

### Resource limits

| Limit | Default | Setting |
| --- | --- | --- |
| Upload size | 20 MB | `MAX_UPLOAD_MB` |
| Rows / columns per dataset | 250,000 / 200 | `MAX_ROWS`, `MAX_COLUMNS` |
| Datasets / stored bytes per user | 25 / 100 MB | `MAX_DATASETS_PER_USER`, `USER_STORAGE_QUOTA_MB` |
| Analyses per user per 24 h | 10 | `DAILY_ANALYSIS_LIMIT` |
| Concurrent analyses per user | 1 | `MAX_CONCURRENT_ANALYSES_PER_USER` |
| Analysis duration | 7 minutes | `ANALYSIS_TIMEOUT_SECONDS` |
| Tool calls / agent rounds per analysis | 16 / 5 | `MAX_TOOL_CALLS`, `MAX_AGENT_ROUNDS` |
| Auth attempts per minute (per address and per account) | 10 | `RATE_LIMIT_AUTH_PER_MINUTE` |
| API requests per minute per user | 240 | `RATE_LIMIT_API_PER_MINUTE` |
| JSON request body | 64 KB | fixed |

The free-tier deployment lowers the upload and row limits; see [DEPLOYMENT.md](DEPLOYMENT.md).

### Transport, headers and errors

- API responses carry `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, a `default-src 'none'` content
  security policy, and HSTS in production. The frontend sets its own CSP and headers.
- Errors share one JSON shape with a request id. Unexpected failures return a generic message;
  stack traces go to the log only. Health endpoints report `ok`/`failed` per dependency and
  nothing else.

### Secrets and logging

- Configuration comes from environment variables. `.env` files are git-ignored. The
  application refuses to start in production with a default or short `SECRET_KEY`, a SQLite
  database, or local-disk storage.
- Logs contain ids, paths, status codes and timings. Request bodies, cookies, query strings
  and dataset contents are not logged, and log fields whose names suggest a secret are
  redacted.

### Dependencies

CI runs `pip-audit` on the backend requirements and `npm audit` on the frontend's production
dependencies. Backend dependencies are pinned to exact versions.

## What is sent to the model provider

The analysis sends Groq: column names and types, per-column summary statistics, a few example
category values per column, the user's question, and the aggregated results of tool calls
(tables of up to twelve rows each). The `filter_rows` tool returns individual rows, so a
question that asks for specific records will send those rows. The raw file is never sent.
Groq's own data-handling terms apply to this content.

## Not implemented

- **Password reset and email verification.** There is no email provider, so a forgotten
  password cannot be recovered and email ownership is not verified.
- **Multi-factor authentication** and single sign-on.
- **Encryption at rest managed by the application.** Data at rest relies on what the database
  and storage providers offer.
- **Audit log** of account and data access.
- **Distributed rate limiting.** The limiter is in-process, which is correct for one instance
  and must be replaced before running several.
- **A strict script policy on the frontend.** The frontend's content security policy allows
  inline scripts, because Next.js prerendered pages need them and nonces would force every
  page to render dynamically. The frontend never inserts API data as HTML
  (`dangerouslySetInnerHTML` is not used), which is the main defence against script
  injection.
- **Malware scanning** of uploads. Files are parsed as data and never executed or served back
  in their original form.
- **Formal compliance** (SOC 2, GDPR tooling, HIPAA). Account deletion removes all of a user's
  data, but there is no data-processing agreement or export-my-data feature.
